Você faz o commit. O resto sai sozinho.

Três workflows do GitHub Actions que testam o projeto, escrevem o changelog e publicam a release com um pacote para download, sem ninguém clicar em nada.

Baixar a última versão Ver os workflows rodando

  1. Push na main

    Um commit chega na branch principal.

  2. CI

    O projeto é verificado a cada push e pull request.

  3. CHANGELOG.md

    O histórico de commits vira um arquivo legível.

  4. Tag v*

    Você decide que é hora de uma versão nova.

  5. Release

    Um .zip publicado, com o changelog como notas.

O que roda, e quando

CI Push e pull request na main

Faz o checkout e executa os passos de build e teste. Se algo quebrar, o pull request mostra antes do merge.

Ver blank.yml
Changelog Push na main

Lê o git log inteiro e reescreve o CHANGELOG.md. O commit do bot leva [skip ci] para não disparar tudo de novo.

Ver changelog.yml
Release Tag que começa com v

Empacota o projeto em um .zip com o nome da versão e publica a release usando o changelog como texto.

Ver release.yml

Teste você mesmo

  1. Mande um commit para a main

    O CI e o Changelog começam na hora.

    git commit -m "feat: minha mudança"
git push origin main

  2. Crie uma tag de versão

    Use um número que ainda não existe. Esse push dispara o workflow de Release.

    git pull # traz o commit do changelog
git tag v1.0.0
git push origin v1.0.0

  3. Baixe o pacote

    Em Releases, a versão nova aparece com o trabalho-devops-v1.0.0.zip anexado. Esta página está dentro dele.

Se a action falhar com erro 403 no push ou na release, ative Settings › Actions › General › Read and write permissions no repositório.
